# Local eight-player stress test — 18 October 2026

The local server sustained eight players and a sixteen-player overload run. Issues were found and fixed: malformed WebSocket traffic could crash an entire world, and departing avatars and repeated motorcycle use leaked client GPU resources. Heavy fights still have a client rendering risk: about 19–27 FPS in the most demanding measured scenes on an M2 Pro, even with adaptive resolution.

## Scope and setup

- Apple M2 Pro, 12 CPU cores, 16 GB RAM; Node 24.20.0; Chrome 155, headless with hardware WebGPU/Metal. One viewport at 1280×720 for the scenario measurements.
- Production build and production server on localhost, isolated SQLite worlds.
- Simulation is authoritative at 60 Hz with 20 Hz player snapshots; worlds have separate processes and databases.
- Boss/swarm measurements use **one full rendered browser plus seven real WebSocket protocol clients**, each with its own identity, input stream, inventory, shooting and ping traffic. The overload adds eight more protocol clients. Separate eight-full-browser results are below.
- Debug gear/spawn/summon controls supplied repeatable encounters. Boss fixtures used extra lives; the combined runs used 1,000 lives while the observer displayed at most 50 marks. Normal ten-life game-over was tested separately. The protocol bots deliberately disconnected and returned to the arena after respawning: their recorded 1006 closes are intentional test churn.
- Early moving/swarm measurements used the `35aa28f` checkout; individual and combined boss runs used `9a369c6`. Later browser, latency, distant worm and cleanup checks used `9026b34` (includes teammates’ intervening changes), followed by the motorcycle cleanup in `b48f95b`. Do not interpret local results as a production-VPS or Internet capacity benchmark.

## Combat measurements

FPS comes from browser animation-frame intervals. Snapshot gaps use timestamps generated by the world server; target spacing is 50 ms. Adaptive resolution remained enabled, reaching 0.65× in combined fights. Values describe each window, not the game’s guaranteed minimum performance.

| Scenario | Players | Window | Average FPS | Frame p95 | Server gap p95 / max |
| --- | ---: | ---: | ---: | ---: | ---: |
| Moving and firing | 8 | 45 s | 37.1 | 33 ms | 64 / 71 ms |
| 42 crawlers, guardian, drones | 8 | 60 s | 20.1 | 83 ms | 57 / 99 ms |
| Queen, up to 16 spiderlings | 8 | 90 s | 37.3 | 33 ms | 61 / 108 ms |
| Carrier, up to 8 gun drones | 8 | 90 s | 27.2 | 67 ms | 64 / 113 ms |
| Colossus, including kill/reward | 8 | 90 s | 34.4 | 50 ms | 64 / 84 ms |
| Worm near the base | 8 | 90 s | 40.1 | 33 ms | 64 / 67 ms |
| Worm hunting at distant crash site | 8 | 90 s | 45.3 | 33 ms | 64 / 67 ms |
| Four bosses + 43 walkers + drones/storms/jet | 8 | 90 s | 21.1 | 67 ms | 53 / 102 ms |
| Four bosses + existing swarm | 16 | 65 s | 19.4 | 67 ms | 64 / 145 ms |

No new browser exceptions or world-process crashes occurred in these completed combat windows. Seven arena bots repeatedly died and rejoined as intended; the eight additional overload clients remained connected throughout their 75-second run. The rendered observer also stayed connected. An earlier overload fixture correctly ended when its shared lives ran out; that window is excluded from the sustained-run table.

Local ping p95 was generally below 6 ms. Ordinary eight-player traffic was roughly 57 KiB/s per client; repeated deaths, corpses, terrain edits and rejoins made the artificial combined fights much heavier (roughly 145 KiB/s for the measured arena client at eight players). This is application payload volume, not wire bandwidth including compression/TLS. A CPU profile of the heavy scene was dominated by rendering/draw submission and GPU buffer work. The combined eight-player world used roughly 5% of one local CPU core during sampled five-second windows. These observations point to rendering as the primary local bottleneck.

## Confirmed defects and fixes

### One bad WebSocket peer crashed the world — fixed in `9a369c6`

With seven healthy peers present, sending JSON `null` from the eighth peer threw while reading the message type. Sending an oversized frame triggered an unhandled `ws` error. Both terminated the world process and disconnected the other players.

The world now rejects invalid top-level message shapes and handles socket protocol errors locally. `tools/server-resilience.test.mjs` forks the actual world worker and verifies null, number, array, missing/non-string type, invalid JSON, oversized frames and invalid UTF-8. Every case leaves all seven healthy clients receiving snapshots. Run:

```sh
node --test tools/server-resilience.test.mjs
npm run build
```

### Avatar resources accumulated after reconnects — fixed in `9026b34`

The floating player-label textures and avatar render bindings survived removal from the scene. Placeholder and held-item models also needed binding cleanup. Disposal now releases those owned resources and cloned skeletons while preserving shared model geometry and materials. This follows the installed renderer’s disposal hooks and [Three.js resource ownership guidance](https://threejs.org/manual/pages/how-to-dispose-of-objects.html).

Before cleanup, rounds 5 to 10 of reconnecting seven players raised textures from 87 to 122, uniform buffers from 10,159 to 17,379, and post-GC JavaScript heap from 134.5 to 164.8 MiB. After cleanup, textures stayed at 52 through 140 reconnects. In the second 70-reconnect window, uniform buffers were 3,647 → 3,672 and post-GC heap 113.1 → 116.6 MiB. Small residual cache/world-resource growth remains; this was not a multi-hour leak proof. All eight players returned each time.

### Motorcycle bindings accumulated on dismount — fixed in `b48f95b`

Ten mount/dismount cycles with seven other players present raised uniform buffers from 3,593 to 5,271 and post-GC heap from 117.4 to 122.0 MiB. The bike removed its scene graph but retained renderer bindings and cloned lamp materials. Cleanup now disposes those per-bike resources while keeping shared geometry, tier materials and pooled headlights. A repeat on the flat bunker floor (to keep movement from loading additional terrain) held geometry and texture counts constant: 612 geometries and 52 textures. Ten cycles changed uniform buffers from 3,896 to 3,902, and no renderer bindings remained for the tagged, dismounted bikes. The earlier repeat on a dune loaded new terrain and was not used to judge leak growth.

## Gameplay and recovery checks

- Eight-player salvage: seven holders could not finish an eight-person step; the eighth enabled completion for everyone. Eight simultaneous take attempts produced one item, owned once.
- Shared chest: eight simultaneous withdrawals of the same item produced exactly one owner, with updates visible to all clients.
- Chat: eight sends reached all eight clients (64 deliveries).
- Death/lives: eight simultaneous deaths consumed eight of the default ten lives; all eight respawned. Two further deaths ended the world and closed all eight sockets with 4410. Rejoining that spent world was refused. Browser game-over and missing-world screens were checked.
- Colossus defeat produced its reward and ten additional lives; a rendered browser used the real inventory and rifle input alongside protocol clients.
- Production server restart: all eight clients reconnected; the browser player’s complete inventory, position and colour matched before/after. The observed browser outage was about half a second in the sampled restart.
- Full build and all eight malformed-message cases passed (nine Node test results including the parent test). The server and avatar fixes deployed successfully; the live version endpoint reported `9026b3430d36ae494563ac46e4b9132a1e84ea92`. [Deployment run](https://github.com/woltsu/dadajam/actions/runs/39140135643).

## Full browser and latency checks

Eight isolated browser contexts with distinct player identities connected to one world. Initial attempts hit prolonged WebGPU initialization stalls under the shared GPU load. In a fresh Chrome process, briefly pausing the three ready render loops allowed the other five to initialize; all eight were then resumed. The final **18.8-second simultaneous movement window** had eight active renderers, each rendering another 145–148 frames, no console errors, no disconnects, and a maximum server snapshot gap of 66.4 ms. Each view averaged 7.8–7.9 FPS while sharing this one GPU (one 1280×720 viewport, seven 800×450). This is a concurrency check, not a prediction of FPS on eight separate computers. Startup under concurrent GPU load remains an unresolved limitation. A forced WebGL2 attempt reached rendering but stalled badly under concurrent load; a clean standalone fallback run is not certified.

A browser then walked, jumped/slid and rode a motorcycle while its WebSocket application messages were delayed by 150–200 ms in **each direction**, preserving order. Seven other clients rode motorcycles normally. All 285 sampled connection checks remained online. Reconciliation offset was 0.39 m at p95, 0.84 m maximum; pending inputs peaked at 59 and returned to 2 shortly after restoring normal delivery. This tests artificial latency/jitter, not packet loss, TCP retransmission or real Internet routing.

The distant worm run started roughly 1,021 m from the base on deep sand. With eight players present and shooting disabled, the worm exercised hunt, rise, air and dive modes. Worm deaths, respawns and terrain edits were observed. The browser averaged 45.3 FPS across 90 seconds (including its return to base after dying), with a 67.2 ms maximum server snapshot gap and no browser errors. Lunge and missile-salvo coverage was not established.

## Playtest assessment

Eight-player server capacity looks suitable for the local playtest based on these runs. The strongest remaining risks are client frame rate during heavy fights and delayed graphics initialization when many renderers compete for one GPU. Carrier combat averaged 27 FPS; the extreme swarm/combined fights averaged 19–21 FPS. Individual spawn/death/shader hitches reached about 1.6 seconds. We did not certify older laptops, Safari/Firefox, packet-loss recovery, a two-hour uninterrupted soak, or production-host CPU/network capacity.

The tests used the latest available code at the stated checkpoints; subsequent team commits need their own smoke check. All test databases and processes were isolated from normal development and production worlds.
